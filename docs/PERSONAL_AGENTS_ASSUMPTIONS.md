# Personal agents (step 18a): assumptions and deviations

1. **SQLite, migration 8.** `jsonb` columns are TEXT JSON (`reminder_offsets`). Migration 8 is appended to `MIGRATIONS` in `apps/server/src/db/index.ts`; it also adds `groups.avail_deadline_at` for the optional scheduling timeout.
2. **Branch base.** `feat/agents` starts from `feat/cubbie-probes` (docs cleanup and read-only inspect tools, not yet on main).
3. **Group project data is group-owned.** Tasks, owners, statuses, points, the due date, and the meeting are shown to everyone in the group already, so `buildContext` puts them in `group` (not in any member's private bucket).
4. **Course items count as shared within the course.** Another member's Canvas items are included only when they are in this group's Canvas course (same rule as before 18a). Everything else from another member reaches the LLM only through `user_memory` rows they marked `visibility='group'` for THIS group.
5. **Group mode never loads private rows, including the asker's own.** The private part of a self-query is answered by a second `buildContext({ mode: 'private' })` call whose reply goes by DM only.
6. **Per-user Google OAuth needs a Web OAuth client.** The existing team client is a Desktop client (loopback only). New env `GOOGLE_USER_CLIENT_ID` / `GOOGLE_USER_CLIENT_SECRET` (Web application type, redirect `PUBLIC_URL/api/google/callback`, scope `https://www.googleapis.com/auth/calendar.freebusy`). Without them, "Connect Google" is hidden and the ICS paste works alone. In Google testing mode every teammate's Gmail must be added as a test user, and tokens expire after 7 days.
7. **One encryption key.** Google refresh tokens and ICS secret addresses are encrypted with the existing `FEED_ENCRYPTION_KEY` (AES-256-GCM, `canvas/crypto.ts`).
8. **Busy blocks never store titles.** Only start, end, and source (`google`, `ics`, `canvas`). Canvas calendar items with `kind='event'` (timed events, not assignment due dates) become busy blocks.
9. **Wiring is pre-done by the lead** so parallel agents do not collide: routers `routes/memory.ts`, `routes/prefs.ts`, `routes/calendar.ts` (mounted on `/api` after auth), `routes/googleCallback.ts` (public, mounted first), job stubs `reminders.ts` `startReminderScheduler()` and `calendarSync.ts` `startCalendarSync()` (started in `index.ts`), screens `CalendarConnect.tsx` and `Memory.tsx` (routed in `App.tsx`, Home rows added), Screen ids `calendar` and `memory`.
10. **REMIND: offsets are normalized, not rejected for order.** `PUT /api/me/prefs` dedupes and sorts `reminder_offsets` descending, then requires 1 to 5 integers of 1 to 336 hours. Unknown body keys (any user id, `can_dm`) are dropped by zod; identity comes only from `tgUser(res)`.
11. **REMIND: quiet hours with equal start and end mean no quiet hours.** Windows may wrap midnight (23:00 to 08:00). During quiet hours a run does nothing for that user; the first run after quiet end sends everything due once and records every offset it covers.
12. **REMIND: date-only due dates are 23:59 in the group's tz.** `groups.due_date` and `tasks.due_date` are `YYYY-MM-DD`; a value with a `T` time is parsed as that local time. Offsets are real elapsed hours (DST-safe), labels use the user's prefs tz.
13. **REMIND: assignment and task lines can duplicate.** `saveAssignment` gives every task the group due date, so a member often gets both `assign:<groupId>` and `task:<taskId>` at the same moment. Per the brief, only identical keys are deduped.
14. **REMIND: late items fire immediately.** An item first seen inside several offset windows (new import, reminders just turned on) is sent once with all those offsets recorded.
15. **REMIND: the scheduler is off when the bot is off.** `startReminderScheduler()` returns null when `BOT_MODE=off` or there is no `BOT_TOKEN` (unless a `send` is injected). Sends are plain text, one message per user per run, 15 minute interval, overlapping runs skipped. Non-403 send errors are logged and retried next run (nothing recorded).
16. **REMIND: `markCannotDm(userId)` in `apps/server/src/prefs.ts`** is the shared hook: any code whose DM fails with Telegram 403 (`isForbidden(err)`, also exported) should call it. `setCanDm(userId, true)` runs on any private `/start`, including `/start reminders` from `start_link`. A plain private `/start` keeps the old intro and appends the reminders confirmation.
17. **REMIND: Mini App.** New `components/DmStart.tsx` (the Start card) and `openTelegram(url)` in `telegram.ts` (prefers `openTelegramLink`, typed optional, else `openExternal`). Settings saves reminder changes on each change with optimistic UI and rollback; the rename part is unchanged.

### CAL agent (calendar connections and busy blocks)

- **CAL-1. Sync backoff lives in memory.** `calendar_connections` has no failure counter or next-sync column, so per-connection backoff (30 min doubling to 12 h) is kept in a Map and resets on restart. `last_error` is persisted (redacted).
- **CAL-2. Busy blocks are merged per source.** Overlapping or touching intervals from one source are merged before storing, so `busy_block_count` counts merged busy times. Capped at 2000 blocks per (user, source).
- **CAL-3. Canvas events last one hour.** `calendar_events` stores only `due_at`, so a Canvas `kind='event'` item blocks one hour from its start. Items whose start is local midnight in `DEFAULT_TZ` are treated as all-day and skipped. Canvas blocks are refreshed for every user with Canvas events on each sync pass, independent of Google or ICS.
- **CAL-4. RRULE support is partial.** DAILY and WEEKLY rules (INTERVAL, COUNT, UNTIL, BYDAY, EXDATE, RECURRENCE-ID overrides) are expanded with wall time kept across DST. MONTHLY, YEARLY and others keep only the first instance; the sync logs a count (never titles or links). Only the last EXDATE line of an event is read (the shared `readIcs` keeps one value per property name). Timed events with no DTEND or DURATION last one hour. Common Outlook Windows TZIDs are mapped to IANA zones; unknown TZIDs fall back to the calendar zone, then `DEFAULT_TZ`.
- **CAL-5. SSRF guard.** ICS links must be https (webcal and webcals are rewritten), on port 443, without credentials, with a hostname (no IP literals, no localhost, `.local`, `.internal`, single-label hosts). Every hop (up to 3 redirects, followed manually) is DNS-resolved and refused if any address is private, loopback, link-local, CGNAT, multicast or IPv4-mapped. DNS rebinding between the check and the connect is not covered. 20 s timeout, 5 MB cap, no conditional GET (no etag column).
- **CAL-6. google_available** is true only when `GOOGLE_USER_CLIENT_ID`, `GOOGLE_USER_CLIENT_SECRET`, `PUBLIC_URL`, `LINK_SIGNING_SECRET`, and a valid `FEED_ENCRYPTION_KEY` are all set (everything the flow needs), not just the client id.
- **CAL-7. OAuth state** is `base64url(json{u, exp, n, p:'gcal'}).hmac`, HMAC-SHA256 keyed with `gcal-state:` + `LINK_SIGNING_SECRET` so it can never be confused with a browser link token. 10 minute expiry. Not single-use (Google codes are single-use already).
- **CAL-8. Disconnecting Google** also revokes the refresh token at Google, best effort; the local token and blocks are deleted either way. If the granted scopes (when Google reports them) lack calendar.freebusy, the callback shows an error and stores nothing.
- **CAL-9. Status per connection shows the total count.** The contract has one `busy_block_count` (all sources, next 14 days, Canvas included), so each connected card in the Mini App shows that total. See AGENTS_CONTRACT_CHANGES.md.
- **CAL-10. ICS parsing lives in a new file** `apps/server/src/icsBusy.ts` (URL guard, safe fetch, busy parser) to keep `calendarSync.ts` readable. `.env.example` was not edited (shared file); the README lists the new env vars.

## SCHED (calendar-prefilled availability, top 3 time poll)

10. **Prefill eligibility.** A member gets `prefill` only if their member row has a Telegram id (seeds excluded) and that id has a `calendar_connections` row or at least one busy block on the grid's 7 days. Link-auth members follow the same rule through their member row. `busy_slots` are only the caller's own; the heatmap never includes busy data.
11. **Prefill hours** come from `PREFILL_START_HOUR` / `PREFILL_END_HOUR` read directly from `process.env` in `apps/server/src/busyRead.ts` (defaults 8 and 22), not added to `env.ts`, to avoid colliding with other agents. The grid itself still shows 9 AM to 10 PM.
12. **The prefill is not saved until confirmed.** The grid opens preselected but nothing is PUT until "Looks right" or the first manual edit, so an unconfirmed prefill does not count as "responded" (and the Group view does not count you yet).
13. **Viable slot** for the time poll means at least two people free for the whole hour (one for a team of one). If no hour is viable, the existing "Nobody's free times overlap yet" message is posted; before this a one-person hour could be locked.
14. **Ranking.** Attendance desc, then duration fit desc (extra contiguous 30-minute slots before and after the hour in which every one of the free people stays free), then earliest. Picks may not overlap; back-to-back hours (4 to 5 and 5 to 6) do not overlap and can both appear.
15. **Time poll state lives in Telegram, not the DB.** While the time poll is open the group status is set to `active` (no meeting row yet), so new saves and the deadline job cannot re-post it, and this survives restarts. The 3 candidate starts are packed into the [Confirm time] callback data (slot index base 36), so Confirm works after a restart without recomputing. `stopPoll` failing with "already been closed" is the double-tap guard.
16. **Deadline.** [Lock in 24h] / [Lock in 48h] buttons on the availability message plus `/deadline 24h|48h|off` (any 1 to 168 hours). The job clears `avail_deadline_at` before proposing times so it fires once.
10. **POLICY: deterministic group classifier, no LLM fallback.** `bot/qa.ts` `classifyQuestion`: (1) a teammate named (full roster name or first name, whole word, possessive ok, not the asker) with a project word (task, part, stuck, done, progress, working on, meeting, ...) and no personal word (due, schedule, class, tonight, free, busy, grades, private, doing, ...) is `group`; (2) any other teammate mention is `member`, the earliest mentioned name wins when several are named; (3) the asker's own name or I/me/my is `self` unless it is only about the project (project word, no personal word, e.g. "what should I work on first?"); (4) everything else is `group`. Names that are common words (Will, May, Bill) can false-positive into `member`; the worst case is the "That's X's to share." line, never a leak.
11. **POLICY: member answers.** When the named teammate has no shared memory and no items in this group's course, the reply is the fixed "That's X's to share." with no LLM call. Otherwise the LLM sees the group project facts plus only that teammate's `membersShared` entry (the asker's own and other teammates' shared rows are dropped) and is told to reply with that line if the facts do not answer.
12. **POLICY: self-question DMs.** The private half is a second `buildContext({ mode: 'private' })` call with teammates' shared rows dropped, sent with `bot.api.sendMessage(askerId)`. The DM is sent before the group reply so the group line is either "Sent you the rest in DM." or the Start hint. A failed DM does not write `user_prefs.can_dm` (REMIND owns prefs).
13. **POLICY: memory parsing.** Remember/forget intents and key labels are parsed with regexes (no LLM). "note" only counts as "note that ...". Messages ending in "?" are never saved. "forget X" deletes the asker's rows whose key or value contains X, or contains every meaningful word of X.
14. **POLICY: DM conversations.** Plain text in a private chat with the bot (not a command, not a pending input) is answered by `bot/dm.ts`. Context = `buildDmContext(ctx.from.id)` in `context.ts`: one `buildContext({ groupChatId: null, mode: 'private' })` for the user's own rows plus one `mode: 'group'` call per group they are a member of (group mode per group so private rows render once and never inside a group section; the per-group skills profile is not included). DM history is kept in memory per Telegram user (last 12 turns, lost on restart) because `agent_messages` is keyed by member id. The DM uses the group nickname when the user is in exactly one group, else "Groupie". `bot/index.ts` got one line registering `dmComposer` after every other handler.
15. **POLICY: group addressing.** A group message is addressed when the nickname or "Groupie" is at the start (optionally after a greeting like hi, hey, thanks, ok), at the end, or anywhere as a whole word in a message of 6 words or fewer; plus @mentions and replies to the bot. A greeting with only the name returns the greeting ("hi Motu" asks "hi").
10. **BRIDGE: personal imports.** A pair code with no group is now a personal import (`/canvas` in a DM, or the Mini App without `groupChatId`). The plan uses `parseAssignment(text, 1, ...)`, so it still has 6 or more steps and ends with "Integrate and proofread". The DM is sent even when the plan fails (it then says so), and the HTTP reply is still 200 "Sent to Groupie. Check your Telegram messages." because the due date was saved and the student got a message. The import row is `imported` when a plan or a calendar item was made, else `failed`.
11. **BRIDGE: calendar items from imports.** Saved as `calendar_events` rows with uid `cubbie-import-<importId>`, due date converted to UTC ISO (the feed's format), `description` null. If the same title and due time already exist for the student (feed or earlier import), no second row is added. The feed poller and `DELETE /api/feed` now leave `cubbie-import-*` rows alone, otherwise the next poll would mark them removed.
12. **BRIDGE: link codes reuse `cubbie_pair_codes`** with a new `purpose` column (`import` default, `link`). Import rejects link codes and link rejects import codes, both as `404 unknown_code`, so a code cannot be used for the other flow.
13. **BRIDGE: one live iMessage link per student.** A new link revokes older tokens. `name` in the link response is the student's member name from any group, else null (pair codes carry no name, and we do not call Telegram for it).
14. **BRIDGE: `/me` contents.** Only the owner's own tasks per group (no other members' task rows or names), group task counts, the next meeting (one whose end is still ahead), and the owner's own `calendar_events` for 7 days. It never reads `user_memory`, `agent_messages`, `busy_blocks`, or other members' calendar rows. Due labels for calendar items use Canvas time (America/Phoenix); group due labels use the group's tz.
15. **BRIDGE: the Groupie token is not a student credential.** It is issued by Groupie to the student and only ever sent back to Groupie, so it is saved by the Skill under HOME (`~/.config/groupie/token`, mode 600) rather than through Cubbie's Secure input. The signing key for `link.py` is the same public `GROUPIE_SIGNING_KEY` in `send.py`.
16. **BRIDGE: rate limits** (in memory, `CUBBIE_LINK_RATE_LIMITS`): link 20 per IP per 10 minutes (checked before the signature), `/me` and `DELETE /link` 120 per IP and 30 per token per 10 minutes.
