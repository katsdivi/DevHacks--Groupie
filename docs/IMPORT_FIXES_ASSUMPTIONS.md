## Rejected import 1

Evidence (read-only: Railway HTTP logs, production DB via `railway ssh`; no secrets or assignment content printed).

- **Request:** `POST /api/cubbie/import` at 2026-10-25T04:18:03Z, UA `groupie-import-skill/1`, request id `EgwxIVeoS1u8hJ-ass7a6g`, ~8.1 KB in, **HTTP 422**, 87 bytes out, 26 ms (no LLM call).
- **Pair code DMMRYD:** purpose `import`, created 04:08:23Z by `POST /api/cubbie/pair-code` from the Mini App (iPhone UA), expires 04:23:23Z (so **not expired**), `used_at` 04:18:03Z, group -5305218337.
- **Group -5305218337 at the time:** status `setup`, `team_size` NULL, no assignment.
- **cubbie_imports row 2:** status `failed`, error `Set the team size first: send /setup in the group.`
- **Signature:** passed (a mismatch returns 401 before this point), so the installed Skill's key matches production. No reinstall needed for the key.
- **Payload shape (7,727 bytes stored):** top keys `pairCode, course, assignment, attachments`; `assignment` has `title, dueAt, pointsPossible, descriptionText, url`; description empty; **no rubric**; 1 attachment `{filename, mimeType (docx), text}` with 2,765 characters of extracted **text**, no `base64` bytes. Schema validation passed.

**Cause:** intake refuses an import while the group has no team size (`no_team_size`, mapped to 422). The Mini App's Canvas screen issues codes without that check (only the `/canvas` command checks it), and the importer claims the code before intake runs, so the failure also burned the code. Cubbie only showed the generic "rejected" line because the Skill does not map 422 / `no_team_size`.

**Fix:** imports land without a team size and the bot asks for it after the task list (import-fixes ROUTING); the code is marked used only after a successful import; every rejection returns one of the documented codes; the Skill maps them. Not a size limit, not a schema mismatch, not a signature mismatch.

## ROUTING

1. **Wrong-app catch lives in one helper.** `catchWrongApp(ctx)` and the pure `matchWrongApp(text)` are in `canvas/bot.ts`. `bot/dm.ts` calls it first in the DM text handler (before pending, history and the model); `bot/qa.ts` calls it first in the group text handler (before the group lookup and `addressedQuestion`, which would otherwise strip "Groupie" and send "import ABC123" to the model). Commands (`/...`) are never caught. Trailing words are trimmed, their whitespace collapsed, and capped at 200 characters (Telegram's copy button holds 256); the code is uppercased.
2. **Which code the reply uses.** The sender's own unused, unexpired import code (whose group, if any, still expects an assignment) is repeated back as is. Anything else (unknown, used, expired, a link code, a lookalike typo, or another user's code) gets "That code expired, here's a fresh one." and a new import code. Another user's code is treated exactly like an unknown one, so the reply says nothing about it and never reuses its group. Fresh code context: in a group chat, this group if Groupie knows it and it still expects an assignment; in a DM, the old code's group if the old code was the sender's and that group still expects an assignment. Otherwise a personal code (plan by DM).
3. **Copy button yes, Open Messages no.** grammY 1.46 / Bot API types 5.0.0 support `copy_text`, so the reply has [Copy] (`InlineKeyboard.copyText`). There is no https link that opens Messages or iMessage from inside Telegram (`sms:` and `imessage:` are not allowed as Telegram URL buttons, and `https://groupie-open-messages` is a placeholder host, not a working link), so Open Messages is omitted; the code block plus [Copy] carry it.
4. **Imports land without a team size.** `no_team_size` is removed from `IngestResult`; intake never rejects for it. The parser plans for the chat head count (member count minus Groupie) when that is 2 to 8, else 4 (`DEFAULT_PARSE_SIZE`). After the task list posts, intake re-reads the group: with a size it posts the join message as before; without one it posts the team size question (same `sizeKeyboard`, "N (everyone here)" first) and no join message (a join message with no size would read "0/0 joined, Everyone's in").
5. **Picking a size after the tasks landed.** New state: `collecting_members` with `team_size` NULL. Tapping a size there sets it, edits the prompt to "Team of N. Love that for us.", posts the join message, then calls `maybeRunSplit` (so a team that already filled in via the Mini App splits right away). A second tap afterwards gets the usual "Team's locked in" alert. `maybeRunSplit` already returns early on a null size, so nothing splits before a size is set. `/setup` in that state re-posts the size question instead of "already set up". `expectingAssignment` is unchanged (still true with zero members, so a second import can replace the task list, same as before).
6. **`/canvas` and the Mini App agree.** `/canvas` no longer checks the team size. `POST /api/cubbie/pair-code` never did; no change there, now covered by a test.
7. **Size prompt tracking uses `groups.status_message_id`.** No schema change. While the team size is unset, the status message is always the size prompt (set by `/setup`, by the post-import question, and by the re-post). `nudgeTeamSize(groupId, messageId)` in the new `bot/teamSize.ts` replies "Tap a team size above first." when the prompt is at most 10 message ids up, and re-posts the buttons when it is further or unknown. The message id gap is a cheap proxy for "messages up": it is reliable in supergroups, only approximate in basic groups, and a misjudged gap only means the buttons get re-posted or the user scrolls a bit. Used by `/join` and `/seed` in the no-size state. `refreshJoinStatus` (called by the Mini App join in `api.ts`) now skips groups with no team size, so a teammate joining in that window cannot overwrite the size buttons with a join message (one-line guard in `bot/joinStatus.ts`, outside my list but not owned by another agent).
8. **For the lead (not my file):** `bot/assignment.ts:68` still replies "Tell me the team size first: send /setup, pick a number, then drop the file again." when a file is dropped before the size. Suggested: drop that check (intake handles a null size now) or call `nudgeTeamSize(group.id, ctx.msg.message_id)`. `sizeKeyboard` and `TEAM_SIZES` moved to `bot/teamSize.ts` (re-exported from `bot/index.ts`) so `intake.ts` can post the question without an import cycle.
9. **`/reset` was already using the join welcome.** It now calls the same exported `sendWelcome(chatId)` as the `my_chat_member` path (WELCOME with [Name me] and [Keep Groupie]); the group row is deleted first, so the nickname goes back to Groupie and nothing is auto-kept. Tested that both payloads match exactly. **Flag:** `/reset` is still gated on `DEV_MODE=true`, but `SIZE_LOCKED`, `alreadySetUp`, intake's `not_expecting`, `/canvas` and the importer all tell users to "send /reset". If production runs without `DEV_MODE`, that command is silent. I did not lift the gate (anyone in a group could wipe it); lead to decide.
10. **TTL 30 minutes.** `PAIR_CODE_TTL_MS` is 30 min. It also covers `/imessage` link codes (same constant). `/canvas`, personal `/canvas` and `/imessage` copy derive minutes from the constant; `Canvas.tsx` expired copy updated. Tests updated: `routes.test.ts` ("within 30 minutes"), `pairCodeLimits.test.ts` (polls for the whole `PAIR_CODE_TTL_MS`; 720 polls at 2.5 s still fit 240 per IP per minute). Reminder and check-in "15 min" strings are unrelated and unchanged.
11. **15 minute pair-code strings in files I do not own (for the lead):** `cubbie-skill/README.md` lines 9, 24, 79; `cubbie-skill/scripts/send.py` line 49 (comment); `API.md` lines 258, 335; `README.md` line 77; `docs/FEATURES.md` line 96; `docs/CANVAS_RECON.md` line 48; `docs/CANVAS_ASSUMPTIONS.md` line 7.

## IMPORT

Logged by the import agent (branch `feat/import-fixes-importapi`).

1. **Error codes and statuses (one status per code, so the Skill mapping is a flat table).** Every non-2xx from `POST /api/cubbie/import` is `{ error, message, requestId }`:
   `bad_signature` 401, `invalid_payload` 400, `payload_too_large` 413, `code_unknown` 404, `code_used` 409, `code_expired` 409, `not_expecting` 409, `rate_limited` 429, `server_error` 500.
   `not_expecting` is an addition to the list (the group already has its assignment; message "This group already has its assignment. Use /reset in the group to start over."). It keeps its own code rather than hiding inside `invalid_payload`, because the payload is fine and the fix is in the group. The Skill must map it.
   Old to new: `unknown_code` to `code_unknown`, `bad_payload` to `invalid_payload`, `imports_off` (was 503) to `server_error` 500, intake `too_short`/`failed`/`busy`/`no_team_size`/`no_group` (were 422 with the reason as the code) to `server_error` 500 with a friendly message that says the code still works. The intake's own messages ("get a new code") are not passed through any more, since the code now stays usable.
   A request with no JSON body (wrong content type) is `invalid_payload`, not `bad_signature` as before.
2. **requestId** is the `x-railway-request-id` header (capped at 64 chars), else 16 random hex chars. The log line is `[import] <requestId> <code>`, optionally followed by a short detail in parentheses (a zod field path like `(assignment.dueAt)`, `(in flight)`, `(intake failed)`); never payload values.
3. **Body-parser errors.** The raw-body JSON parser runs at the app level before the import router, so its errors skip the router. `canvas/routes.ts` exports `cubbieImportErrors` and `index.ts` mounts it next to the router (`app.use('/api/cubbie/import', cubbieImportRouter, cubbieImportErrors)`): one more line in `index.ts` than "body limit line only", needed for the 413 JSON. `canvas/testApp.ts` mirrors both changes. The handler drains the request and sets `connection: close` so the client reads the 413 instead of a reset.
4. **Body limit** is now 15 MB. The parser line is shared with `/api/cubbie/link`, whose bodies are tiny, so the link route gets 15 MB too.
5. **Used only after success.** A per-process in-flight `Set` of codes locks the code from the last synchronous check until the import's work finishes (even past the 25 s timeout answer). A second request with the same code while it runs gets `code_used` ("being imported right now"). `used_at` is set only when the group intake returns ok (or a personal import made a plan or saved the calendar item), with a plain `UPDATE ... WHERE used_at IS NULL` that ignores expiry, so a slow import that crosses the 15 minute line still counts. On `invalid_payload`, `not_expecting`, `server_error` and every intake failure the code stays usable. Groupie runs one Railway instance, so the in-memory lock is enough; two instances would need a `claimed` column. `claimPairCode` is no longer used by the importer (left in `pairCodes.ts` untouched).
6. **Mini App status after a failure:** `pairCodeStatus` shows the latest import row, so after a failed import it reports `failed` while the code is in fact reusable. That screen belongs to another agent; worth a line of copy there ("try again with the same code").
7. **Personal imports** (code made in a DM) now answer `server_error` when nothing was made (no plan and no calendar item); before they answered 200. The DM still goes out as before. Files and the too-big line are group-only.
8. **Size caps** moved out of the schema into the importer so a big file is dropped, not the whole import: base64 over 10 MB decoded (`MAX_ATTACHMENT_BYTES`), text over 60,000 chars (`MAX_ATTACHMENT_TEXT`, new shared constant), and attachments past the first 5 (`MAX_ATTACHMENTS`; the schema now allows up to 50 in the array). Each dropped one counts toward the group line "One file was too big to bring over. Drop it here if you want everyone to have it." (a plural line for more than one).
9. **Schema tolerance** (`packages/shared/src/canvas.ts`): all objects `.loose()` (zod 4), `rubric` and `attachments` optional, `assignment.description` read when `descriptionText` is empty or missing, `dueAt` may be missing (treated as null), `course.code` may be null, a bad `url` or `pointsPossible` becomes undefined/null instead of failing, attachment `filename`/`mimeType` default when missing. The attachment `refine` (needs text, base64 or url) is gone: such attachments are ignored with the log line `[import] attachment with no text, bytes, or link ignored`. A url-only attachment is still listed as a link, never fetched. `dueAt` stays strict ISO with offset, since it is authoritative.
10. **Files after a group import** run inside the intake's success callback in `importer.ts` (so the task list is already up): bytes attachments within the cap go out via `sendDocument` with caption "Here's the assignment from Canvas." (over Telegram's 50 MB upload limit: a line saying so; unreachable today with the 10 MB cap). If no attachment came as bytes (text only, or none at all) the group gets "Pulled the assignment text from Canvas. Drop the PDF here if you want everyone to have the file."
11. **Migration 11** (the 11th `MIGRATIONS` entry in `db/index.ts`, `user_version` 11, right after the dm_messages one) adds `groups.canvas_import_id` (the import row that gave the group its assignment), `groups.canvas_file_at` (when a dropped file was attached), and `groups.assignment_file_id` / `assignment_file_name` / `assignment_file_mime` (the Telegram file behind the current assignment). `db/schema.ts` is touched for these five columns only. If another branch also appends a migration, the merge keeps both and their order sets `user_version`. A group pointer (not inference from `cubbie_imports.group_chat_id`) because `/reset` deletes the group row, which clears the pointer, while old import rows stay. "Text only" is derived from the stored payload: no attachment has `base64Length`.
12. **Dropped file after a text-only import** (`bot/assignment.ts`, logic in `canvas/fileAttach.ts`): the first readable file in a group whose assignment came from a text-only Canvas import is attached: reply "Got the file, everyone can grab it here." (the file is already in the chat, so nothing is re-uploaded or stored besides `canvas_file_at`). Any later file in a group whose assignment came from Canvas passes through to the other handlers and never starts a second task list (this also covers bytes imports). Similarity: lowercased word tokens of 3+ letters/digits, Jaccard index against each imported piece (description, each attachment's text) and against all of them joined, best score wins; below 0.5 the file "clearly differs" and the group gets "Update the tasks from this file?" [Update] [Keep current]. Scans and near-empty files (under 50 non-space chars) and files over 20 MB are attached without the question. The pending text lives in memory per group (a restart drops the question, and a late tap answers "That question expired. The current tasks stay.").
13. **[Update]** cannot use `ingestAssignment` (it refuses a group that already has an assignment, and `intake.ts` is read-only), so `updateTasksFromFile` does parse (with the Canvas rubric, team size or 4 when none is set yet) plus `saveAssignment`, keeps the Canvas due date, posts the task list, restores the group status that `saveAssignment` resets, and re-splits (`computeSplit`, `applySplit`, `postSplitCard`) only if the group was at `split_ready`, `scheduling` or `active`. A failed parse keeps the current tasks. [Keep current] edits the question to "Keeping the current tasks." and does nothing else. Nothing is fetched from Canvas.
14. **Fixture** `fixtures/cubbie/import_live_shape.json`: the live top-level and nested keys with every value replaced by placeholders (placeholder course, title, ids and a placeholder attachment text long enough to clear the intake's 50 character floor).
15. **Assignment file for a later re-send (lead's addition).** Columns on `groups` (above), not a new table: one current assignment per group, and `/reset` already deletes the group row, so they clear with it; a new Cubbie import also clears them. Set when a dropped file becomes the assignment (`readAssignment` returns true once the task list lands), when a dropped file attaches to a text-only import, and from the `sendDocument` result after a bytes import (the first file that posts). `canvas/assignmentSource.ts` exports `assignmentSource(groupId)` returning `{ fileId?, fileName?, mimeType?, canvasText?, title? }`, reading only that group's row and its own import row (the import must be `imported` and belong to the same group). `canvasText` is the stored payload's description plus each attachment's text, joined by blank lines. No fetch command was built.
16. **Update wording.** The task list posted after [Update] starts with "Updated from the file." because the stock footer ("Next, everyone adds their details...") is shared with the first task list.
